# 场景协作编辑冲突处理规范

面向使用 Atlas Render 的场景编辑器团队。输入是两个编辑者从同一修订出发、其中一人先保存时，另一人的创作意图如何继续成立；输出是可执行的操作顺序、失败判定和证据要求。

> **前提声明**：本文所有标为「现行」的做法只使用本仓库已经实现的 HTTP 接口。服务当前**没有**局部合并、PATCH、修订历史、场景摘要、素材恢复或撤销能力（观测结果见第 2 节，能力边界见第 7 节）。第 8 节全部是「建议、未实现」，不得据此假设线上服务能接受增量文档或自动合并。

---

## 1. 结论

1. `PUT /v1/scenes/{id}` 接收**整份文档**，用 `expectedRevision` 做前置条件。服务只能判断「你提交时看到的修订号是否仍是当前修订号」，**不能判断你的文档里有没有别人的改动**。因此 409 是安全网，不是合并。
2. 推荐流程是：**编辑前固定基线 → 记录意图 → 被 409 拒绝后重新读取当前文档 → 按图层 ID 把意图重放到当前文档上 → 整份提交 → 冻结快照并用像素比较复核**。下文称为「人工整合」。
3. **整份重放**（把过期草稿改个 `expectedRevision` 再提交）会通过修订检查，同时静默删除先保存者的图层、层序和改名。只在作者明确决定丢弃他人改动时使用，并且必须留证。
4. 图层重排、祖先变换、素材退役三种改动不能按字段直接拼接：层序决定遮挡、祖先变换改变后代局部坐标的含义、素材退役改变引用闭包。三者都需要按**画面意图**重算，再用像素比较确认。
5. `archived → active` 只是状态切换并递增修订，**不保存、不还原任何内容**。恢复后必须重新读取当前文档；用归档前的旧检出回放，才是覆盖他人修改的动作。归档时刻的画面应由归档**前**冻结的快照承载。
6. 基线文档建议在开工时冻结一个快照取得：快照文档不可变、摘要稳定，且可以与后续渲染做像素比较。这与第 8 节建议的修订历史是两件事——快照是现行能力，历史读取不是。

## 2. 服务当前的事实基线

以下行为均在 `scripts/conflict_demo.py` 中对真实进程观测得到，可复现（第 10 节）。

| 事实 | 观测 | 对协作的含义 |
|---|---|---|
| 保存接口只有整份 `PUT` | `PATCH /v1/scenes/{id}` 返回 405；`POST /v1/scenes/{id}/merge` 返回 404 | 不存在「只提交我改的那一层」的现行通道 |
| 冲突判定只看修订号 | 提交与已接受基线逐字节相同的文档，但 `expectedRevision` 落后，仍返回 409 `scene revision changed` | 409 不代表内容冲突，只代表基线过期；不能据此推断谁改了什么 |
| 前置检查的粒度为整个场景 | 任意一层、场景名、画布背景变化都会让修订号 +1 | 无法用修订号定位改动范围，必须自己比较文档 |
| 场景名属于每次保存的载荷 | 旧草稿以新修订提交会把场景名改回旧值 | 整合时名字也要一起决定，不能只盯图层 |
| 保存是「创建或替换」 | 对不存在的场景用 `expectedRevision: 0` 提交会**创建**它；用非零修订提交返回 409 | 拼错场景 ID 不会 404，会新建一个空场景；编辑器必须校验目标 ID |
| 空操作也会递增修订 | 原样提交当前文档返回修订 +1 | 修订号不能当内容版本号用；记录基线要用文档摘要或快照摘要 |
| `GET /v1/scenes/{id}` 无摘要、无 ETag | 响应头没有 `ETag`；`PUT` 上的 `If-Match` 被忽略，照样 200 | 客户端必须自己对返回的文档算摘要 |
| 返回文档经过结构补全 | 组也会补上 `fill`、`width: 0`、`transform` 的零值 | 客户端摘要要以 **GET 返回值**为准，不能拿自己发送的 JSON 当基线 |
| 快照文档不可变 | 场景后续改色、换序、归档后，`GET /v1/snapshots/{id}` 的文档与摘要均不变；快照被撤回后文档仍可读 | 快照可作为可信的基线文档和画面证据 |
| 同一修订可冻结多个快照 | 两个快照 ID 不同、摘要相同 | 「同一内容」可以用摘要判等，不必比较 ID |
| 同一快照重复渲染字节相同 | 同快照同 scale 两次渲染的 PNG 字节一致（artifact ID 不同），`POST /v1/compare` 为 0 | 像素比较可以作为整合是否保留意图的客观证据 |
| 素材退役是全局且不可逆 | 同 ID 重新上传返回 409 `asset id already exists`；`/revive` 返回 404 | 没有「恢复原素材」的现行能力 |
| 退役素材会阻塞整份保存 | 即使只改背景，只要文档仍引用退役素材，保存返回 409 `scene references unavailable asset`，冻结返回 409 `snapshot references unavailable asset` | 冲突处理期间若素材被退役，另一位作者连无关改动都提交不了 |
| 归档期间禁止写入 | 保存返回 409 `scene is archived`，冻结返回 409 `scene revision or state changed` | 归档是写入闸门，不是内容快照 |
| 恢复不还原内容 | 恢复后文档与归档前一致，修订继续递增 | 恢复不等于撤销 |
| 交换包导入只新建场景 | 目标 ID 未使用时创建 `active` 场景、修订 1；目标已是规范场景返回 409 | 导入是分叉，不是回滚；也不落地原快照记录 |
| 事件不含修订与摘要 | `GET /v1/events` 仅 `sequence/kind/subject/at` | 事件不能用来重建「谁在第几修订写了什么」 |

## 3. 冲突的本质

把一次保存写成四元组：

```
(baseRevision, baseDocument, intendedDocument, intent)
```

服务端只比较 `baseRevision` 与当前修订：

- 相等 → 写入整份 `intendedDocument`，修订 +1；
- 不等 → 409，什么都不写。

于是存在两个都「成功」但语义完全不同的动作：

| 动作 | 提交的文档从哪来 | 服务端看到 | 实际效果 |
|---|---|---|---|
| 整份重放 | 从 `baseDocument` 派生，只把 `expectedRevision` 换成当前值 | 修订号正确 | 把当前文档替换成基线 + 我的改动，**抹掉先保存者的一切** |
| 人工整合 | 从**当前文档**派生，再把我的意图应用上去 | 修订号正确 | 保留先保存者的改动，同时让我的意图成立 |

两者都是合法 `PUT`，服务无法区分，区别完全在客户端如何构造 `intendedDocument`。这就是规范存在的理由。

**因此「保留创作意图」不是协议特性，而是文档构造方式 + 复核证据。** 相关建议（摘要前置条件、服务端三方合并）见第 8 节，在它们实现之前不得把责任推给服务。

## 4. 推荐流程：意图记录 → 重放意图 → 整份提交 → 像素验证

### 4.1 编辑开始（每位作者）

1. `GET /v1/scenes/{id}`，记录 `revision` 与返回文档的规范化摘要（对自己的 JSON 做键排序后再哈希，或直接用第 2 步的快照摘要）。
2. 若场景处于 `active`，立刻 `POST /v1/scenes/{id}/snapshots`，保存返回的 `snapshot.id` 与 `snapshot.digest`。这是**不可变基线**，也是后续像素比较的对照。冻结要求全部素材可用且场景 `active`；不满足时按第 4.5 节处理。
3. 在编辑器本地记录意图，而不是只记录最终文档：

```json
{
  "sceneId": "emblem",
  "baseRevision": 7,
  "baseSnapshot": "snap-00000012",
  "baseDigest": "…",
  "operations": [
    {"op": "insert-before", "layerId": "over", "newLayerId": "halo"},
    {"op": "set-fill", "layerId": "over", "field": "color", "value": "#7A3FA0"},
    {"op": "translate-world", "layerId": "tile", "dx": 40, "dy": 0}
  ],
  "assetIntent": {"ribbon": "must-stay-same-bytes"}
}
```

意图记录的关键是把**世界坐标位移、目标层 ID、素材期望字节**写清楚。只记录「局部 `x=40`」在祖先变换变化后会变成另一种画面（第 5.2 节）。

### 4.2 保存被 409 拒绝时

1. **禁止**直接把 `expectedRevision` 改成当前值再提交同一份文档。
2. `GET /v1/scenes/{id}` 重新取得当前文档和修订号。
3. 取基线：优先用 4.1 的快照文档；若没有快照，只有本地缓存的基线文档；若两者都没有，**停止自动整合**，向另一位作者索取基线或改为人工比对，因为无法区分「当前是我的改动」和「当前是别人的改动」。
4. 判定改动是否相交（第 4.3 节）。不相交则按 ID 重放；相交则进入作者决策。
5. 生成整合文档后，先本地校验：图层 ID 全树唯一、非组节点尺寸为正、多边形点在本层边界内、变换 `scaleX/scaleY` 显式非零、渐变端点不重合、素材引用都是 `available`。这些是本服务会以 400/409 拒绝的硬约束。
6. 以**当前修订**提交整份文档。收到 409 说明期间又有人保存，回到第 2 步；不要循环重试超过 1 次，第二次 409 应转人工。
7. 提交成功后冻结快照，渲染并与基线快照做 `POST /v1/compare`。预期差异应只覆盖本次意图涉及的图层；出现额外区域的差异说明整合引入了非预期改动。

### 4.3 整合判定表

| 情形 | 判定 | 现行做法 |
|---|---|---|
| 两人改不同图层、互不为祖先/后代，层序关系未变 | 可直接按 ID 重放 | 保留当前层序，替换我的图层字段 |
| 两人都改同一图层同一字段 | 内容冲突，需作者决定 | 逐字段列出基线与双方取值，选择一方或新值；不允许「后写覆盖」当默认 |
| 我插入图层，对方改了相邻图层 | 层序冲突，需作者决定插入点 | 按「相对锚点」表达插入：`before: over` 或 `after: under`，而不是绝对下标 |
| 对方删除我编辑的图层 | 删除/编辑冲突 | 二选一：接受删除并记录我的内容到注释，或恢复图层并说明；不能静默复活或静默丢失 |
| 我删除、对方编辑 | 同上，方向相反 | 同上 |
| 对方的改动在我的祖先链上（父组变换/透明度/裁剪） | 祖先变换冲突 | 重算我的局部值以保持世界坐标意图，见 5.2 |
| 对方改了素材状态（退役） | 引用闭包冲突 | 见 5.3，先解决素材再提交 |
| 对方归档 | 写入被闸门阻挡 | 等待恢复或改到分叉场景；不得把归档当成对我草稿的确认 |
| 对方改了场景名 | 名称冲突 | 名字与文档一起整份提交；整合时必须显式选定名字 |
| 双方改动画布尺寸/背景 | 全局字段冲突 | 需作者决定；改变尺寸会让所有快照比较失效（比较接口拒绝不同尺寸） |

### 4.4 提交后的记录（便于复盘和下一轮冲突）

每次整合提交至少记录：场景 ID、旧修订、新修订、基线快照 ID/摘要、整合后快照 ID/摘要、意图列表、逐图层取舍、像素比较结果（`changedPixels`、`maxDelta`、`meanDelta`）、决策人。服务的事件流只有 `scene.saved` 与主体 ID，不含这些信息，必须由编辑器侧留证。

### 4.5 基线快照取不到时

- 场景已 `archived`：不能冻结。先恢复（会递增修订），再冻结；恢复本身不改内容（第 6 节）。
- 文档引用了退役素材：不能冻结，也不能保存。按 5.3 处理引用后再冻结。
- 素材缺失/不可用导致冻结 409：说明文档引用的素材从未导入或已退役，先修引用，不要绕过。

## 5. 三类结构性改动对画面含义的影响

### 5.1 图层重排与插入

图层按文档顺序 source-over 合成。**同一组图层集合，顺序不同就是不同画面**；插入一层还会改变其后所有层的遮挡关系。整份重放的危害在这里最直接：它以「基线 + 我的改动」替换当前文档，等于把对方的插入和顺序整体丢弃。

复现（`examples/conflict/layer-order/case.json`，`--scenario layer-order`）：

- 基线：`under`、`over` 两个矩形。
- A：在两者之间插入半透明椭圆 `halo`，并把场景名改为「层序冲突 v2」。
- B：只把 `over` 的颜色改为 `#7A3FA0`。

| 动作 | 结果 |
|---|---|
| B 以基线修订保存 | 409 `scene revision changed`（即使 B 的文档与基线逐字节相同也是 409） |
| B 整份重放（改修订号） | 200，修订 3，图层 `[under, over]`，`halo` 消失，场景名回退为「层序冲突」；与 A 的画面差 **9328 像素**，`maxDelta 200` |
| B 人工整合（保留 halo、保留 A 的名字，只改 over 颜色） | 200，修订 4，图层 `[under, halo, over]`，`over` 为 `#7A3FA0`；与 A 的画面差 8000 像素（即 B 的改色意图），与整份重放的结果差 **1328 像素**（halo 的遮挡区域） |

结论：重放与整合的差异不是「风格差异」，而是 1328 个像素上有没有 A 的图层。编辑器必须按 ID/锚点表达层序意图，不能按数组下标重放。

### 5.2 祖先变换

服务把局部变换按「缩放 → 旋转 → 平移」组成矩阵，再叠加父矩阵；命中判定用累积矩阵的逆映射。**父组旋转后，后代同一局部字段对应不同的世界方向。** 因此「把局部 `x` 设为 40」不是一个可移植的意图。

复现（`examples/conflict/ancestor-transform/case.json`，`--scenario ancestor-transform`）：

- 基线：组 `frame` 位于 (60,60)，子矩形 `tile` 尺寸 40×20，局部 (0,0)。
- A：把 `frame.degrees` 改为 90。
- B：想在世界坐标把 `tile` 向右移动 40；在基线文档里写作 `tile.transform.x = 40`。

`tile` 左上角的世界坐标（脚本独立计算，用与服务相同的矩阵顺序）：

| 方案 | 锚点 (x,y) | 世界包围盒 x | 世界包围盒 y |
|---|---|---|---|
| 基线 | (60,60) | [60,100] | [60,80] |
| A 旋转 90° | (60,60) | [40,60] | [60,100] |
| B 的世界意图（未旋转） | (100,60) | [100,140] | [60,80] |
| 整份重放（B 的文档） | (100,60) | [100,140] | [60,80] |
| 逐字段合并（旋转 + 局部 `x=40`） | **(60,100)** | [40,60] | [100,140] |
| 意图重算（旋转 + 局部 `y=-40`） | (100,60) | [80,100] | [60,100] |

三种提交都返回 200（修订 3、4、5），服务无从判断：

- **整份重放**：B 的位移成立，但 A 的旋转被丢弃；
- **逐字段合并**：A 的旋转保留，B 的「右移」变成「下移」，锚点从 (100,60) 漂到 (60,100)；
- **意图重算**：保留旋转，并把世界位移反解为局部 `y=-40`，锚点与 B 的世界意图一致；矩形本身随祖先旋转，这一取舍需要作者确认。

像素证据：两两比较均为 1600 个改变像素（`maxDelta 225`），因为三种结果的方块落在不同区域。**只有渲染比较能暴露差别，字段 diff 不能。**

操作规则：

1. 意图记录世界坐标位移/尺寸，局部值只是「在当前祖先链下的编码」。
2. 整合时若祖先链上任何节点的 `transform`、`opacity`、`clip` 与基线不同，必须重算局部值，不能复制我的局部字段。
3. 重算后渲染，与「我的意图在基线上的画面」比较锚点或包围盒；不一致就视为未整合成功。
4. 若对方把图层移到另一个父组，局部坐标的含义整体改变，等同于重新放置，必须作者确认。

### 5.3 素材退役

素材是 `available → retired` 的单向状态，同 ID 不可替换内容，快照冻结时复制字节。退役**不影响已有快照的渲染**，但会影响一切新的保存与冻结。

复现（`--scenario asset-retirement`）：

| 动作 | 结果 |
|---|---|
| 退役前冻结并渲染 | 成功 |
| 退役后再次渲染退役前的快照 | 成功（闭包已固定） |
| 退役后用仍引用 `ribbon` 的文档保存（即使只改背景） | 409 `scene references unavailable asset` |
| 退役后冻结 | 409 `snapshot references unavailable asset` |
| 同 ID 重新上传相同字节 | 409 `asset id already exists` |
| `POST /v1/assets/ribbon/revive` | 404（无此入口） |
| 相同字节以新 ID `ribbon2` 上传，图层改指 `ribbon2` | 200；与退役前快照比较 **0 个改变像素** |
| 删除该图层 | 与改指结果比较 1600 个改变像素 |
| 把退役前快照的交换包导入同一服务 | 409 `destination asset conflicts with package` |

结论：

1. 「恢复退役素材」不是现行能力。同字节新 ID 可以做到**像素不变**，但素材谱系、场景文档和快照摘要都变了；这是新的创作决定，不是撤销。
2. 删除图层是最省事但会改变画面的选择，必须作者确认。
3. 冲突整合期间若遇到退役引用，先让素材负责人决定「改指 / 删除 / 换用其他素材」，再提交；不要为了通过保存而临时删除引用。
4. 退役前冻结的快照是唯一能证明「当时画面」的载体；归档或清理前应确认有快照。

### 5.4 三类改动汇总

| 维度 | 图层重排/插入 | 祖先变换 | 素材退役 |
|---|---|---|---|
| 影响范围 | 同组内其后所有层 | 整棵后代子树 | 所有新保存与新冻结 |
| 整份重放的后果 | 删除对方插入、恢复旧层序 | 丢弃对方旋转/缩放，位移方向可能改变 | 若对方刚改指新素材，会被改回退役 ID 并直接 409 |
| 逐字段/按下标合并的后果 | 插入点错位或覆盖同 ID | 世界意图漂移（右移变下移） | 引用失效或谱系混杂 |
| 可用的判等依据 | 图层 ID 序列 | 累积矩阵/世界包围盒 + 像素 | 素材 ID + 摘要 + 像素 |
| 现行复核手段 | 冻结快照 + `POST /v1/compare` | 同上 | 同字节时像素为 0，仍须记录谱系变化 |
| 需要人工决策的点 | 插入锚点、同 ID 冲突 | 最终锚点与朝向 | 改指、删除还是换素材 |

## 6. 归档与恢复的语义边界

`POST /v1/scenes/{id}/state` 只做状态切换：

- `active → archived`：修订 +1，此后保存与冻结都 409；
- `archived → active`：修订 +1，**文档原样保留**；
- 对已是目标状态的场景重复提交：返回 200，**修订不变**（对齐幂等）；
- 任何一次 `PUT` 即使内容完全相同，也会修订 +1（写入不幂等）。

复现（`--scenario archive-restore`）：

| 动作 | 结果 |
|---|---|
| A 改背景为 `#103040`，保存并冻结 | 成功 |
| B 归档 | 200，修订 +1 |
| 归档期间保存 / 冻结 | 409 `scene is archived` / 409 `scene revision or state changed` |
| B 恢复 | 200，修订继续 +1；文档仍是 A 的版本，不回到任何更早内容 |
| 再次提交 `active` | 200，修订不变 |
| B 用归档前的旧检出、以恢复后的修订保存 | **200**，背景被静默改回 `#F5F1E8`，与 A 的画面差 9600 像素 |
| A 用归档前快照导出交换包并导入 | 新场景、修订 1；规范场景修订不变 |
| 用规范场景 ID 作导入目标 | 409 `destination scene already exists` |

规范：

1. **归档不是快照**。归档时刻的可视内容只能由归档前冻结的快照证明。要「保留归档时的画面」，就在归档前冻结。
2. **恢复不是撤销**。恢复不改内容、不回退修订、不删除他人编辑。恢复后必须重新 `GET` 当前文档，按第 4 节整合。
3. **禁止把旧检出当作恢复内容**。缓存文档的修订号一定落后；改修订号重放就是覆盖（上表第 6 行）。
4. **回滚只能分叉**。确实需要回到旧版本时，用该版本快照的交换包导入为新场景 ID，作为分叉继续工作，并在名字/记录中标注来源快照；不要覆盖规范场景。
5. **归档前检查引用**。归档期间不能冻结；若引用素材在归档期间退役，恢复后第一次保存会被 409 拦住，需先按 5.3 处理。
6. 归档期间读取不受限：`GET /v1/scenes/{id}`、`GET /v1/snapshots/{id}`、导出交换包仍可用。归档只关闭写路径。

## 7. 现行可调用的做法（只使用已实现接口）

| 目的 | 现行调用 | 语义与限制 |
|---|---|---|
| 取当前文档与修订 | `GET /v1/scenes/{id}` | 返回补全后的文档；无 ETag/摘要字段；不存在返回 404 |
| 保存整份文档 | `PUT /v1/scenes/{id}`，体含 `name`、`expectedRevision`、`document` | 修订不匹配 409；场景归档 409；引用不可用素材 409；校验失败 400；未知字段 400 |
| 取得不可变基线 | `POST /v1/scenes/{id}/snapshots`，体含 `expectedRevision` | 要求 `active` 且素材可用；返回快照文档与摘要；同修订可多次冻结 |
| 读历史文档 | `GET /v1/snapshots/{id}` | 只覆盖「冻结过的那一刻」；不是任意修订历史；撤回或归档后仍可读 |
| 归档 / 恢复 | `POST /v1/scenes/{id}/state` | 只切状态；写入被闸门阻挡；恢复不还原内容 |
| 复核画面 | `POST /v1/compare`，体含两个 artifact ID | 只比较已渲染结果；尺寸不同 409；结果已清理 410 |
| 取得可比较结果 | `POST /v1/jobs` + `GET /v1/artifacts/{id}` | 同快照同 scale 渲染字节稳定；作业幂等键与场景保存无关 |
| 导出/导入分叉 | `GET /v1/snapshots/{id}/package`、`POST /v1/imports/{id}` | 导入目标是新场景且必须未使用；不落地原快照；共享素材必须可用且同内容；导入只增加场景，不增加快照记录 |
| 证据留存 | 上述快照 + 结果 + 事件 | 事件只有 `kind/subject/sequence/at`，不含修订与摘要 |

现行做法明确**不包含**：

- 局部合并 / 增量文档 / 按图层 PATCH；
- `If-Match` 或场景摘要前置条件；
- 修订历史列表或历史文档读取；
- 素材恢复、素材别名、素材谱系查询；
- 归档前内容的自动还原；
- 任意撤销 / 重做；
- 场景分支的显式模型（只有「导入到新 ID」这一种近似）；
- 场景保存的幂等键。

## 8. 建议新增能力（均未实现，不得假定可用）

以下按优先级排列。每条都说明为什么现行做法不够、建议语义和验收标准；在实现并写入 `docs/api.md` 之前，编辑器只能按第 4 节处理。

### 8.1 场景文档摘要与条件提交（优先级最高）

- **现状缺口**：场景没有摘要字段，`If-Match` 被忽略；客户端无法用「内容」表达前置条件，空操作也会递增修订。
- **建议语义**：`GET /v1/scenes/{id}` 返回 `documentDigest`；`PUT` 接受 `expectedDocumentDigest`（与 `expectedRevision` 至少一个，二者都提供时都必须匹配）；不匹配返回 409 并在响应体给出当前摘要。
- **收益**：能区分「修订变了但内容与我基线一致」与「内容真的变了」，减少无意义人工整合；重试可安全判等。
- **验收标准**：内容相同但修订落后的保存仍可用摘要匹配成功或返回明确的 `content-unchanged` 分支；摘要稳定跨进程重启；返回文档补全后摘要仍一致。

### 8.2 服务端三方合并（带预演）

- **现状缺口**：只能整份覆盖，合并逻辑分散在各自编辑器，无法审计。
- **建议语义**：`POST /v1/scenes/{id}/merges`，体含 `baseRevision`/`baseDocumentDigest`、`operations`（按图层 ID 的 set/insert-before/insert-after/delete、祖先链变更、素材引用变更）、`dryRun`。响应返回合并后的完整文档、逐操作结果（applied/conflict）、冲突路径与双方取值；`dryRun: true` 不写入。真正提交时才递增修订。
- **约束**：服务端不猜测意图。祖先链变化时对后代的局部值要么拒绝自动合并并标为 conflict，要么要求操作显式给出世界坐标意图，由服务端重算。
- **验收标准**：`dryRun` 不改变任何状态和事件；相同请求在并发保存后返回冲突而非覆盖；合并结果通过 `scene.Validate`；冲突列表能定位到图层 ID 与字段路径。

### 8.3 修订历史读取

- **现状缺口**：只能通过事先冻结的快照获得历史文档；没冻结就无法重建基线。
- **建议语义**：`GET /v1/scenes/{id}/revisions`、`GET /v1/scenes/{id}/revisions/{n}`，返回每修订的文档摘要、时间、操作者标识（若引入）与差异摘要。
- **约束**：需要新的持久化布局和历史保留策略；要考虑容量（当前整状态 JSON 原子替换）。不得改变既有归档/恢复语义。
- **验收标准**：历史只读；与快照摘要能互相校验；历史截断策略明确且事件编号不重用。

### 8.4 图层级素材固定与谱系

- **现状缺口**：图层只有 `assetId`；素材退役后只能改指新 ID 或删除；同字节改指像素相同但谱系不可见。
- **建议语义**：图片图层可携带 `assetDigest` 作为期望内容；冻结时记录素材谱系（原 ID、改指链）。新增 `GET /v1/assets/{id}/lineage`。
- **验收标准**：摘要不匹配时保存 409 且不写入；改指操作在快照中可追溯；不影响既有快照渲染。

### 8.5 素材恢复/别名（严格同内容）

- **现状缺口**：`/revive` 不存在；同 ID 重传 409；运营误退役只能改指新 ID。
- **建议语义**：`POST /v1/assets/{id}/reinstate`，要求提供原摘要且与记录一致，只把状态改回 `available`，不改变字节和谱系；响应包含退役期间受影响的场景列表（只读查询）。
- **验收标准**：异内容恢复 409；恢复不改变已有快照；恢复事件包含原退役事件序号，便于审计。
- **明确不做**：不允许用恢复入口替换内容，否则会破坏「同 ID 内容不可替换」的既有不变量。

### 8.6 归档/恢复的显式语义

- **现状缺口**：`state` 响应没有前状态；恢复与「撤销」在客户端容易被混淆；归档时无法附带「归档依据快照」。
- **建议语义**：状态响应增加 `previousState` 与 `previousRevision`；`archived → active` 可接受 `expectedDocumentDigest` 以确认恢复的是预期内容；事件增加修订与摘要。
- **验收标准**：恢复路径无法修改文档；响应能直接证明「内容未变」。

### 8.7 场景保存幂等键

- **现状缺口**：网络重试可能导致同一整合被提交两次，形成两个修订；只有作业有幂等收据。
- **建议语义**：`PUT /v1/scenes/{id}` 接受 `Idempotency-Key`，同键同语义返回原修订，同键不同语义 409。
- **验收标准**：重试不产生额外修订和事件；键在进程重启后仍有效；键空间与作业收据隔离或明确共享语义。

### 8.8 审计与预演接口

- **事件增强**：`revision`、`documentDigest`、`actor`（若引入认证）。
- **预览**：`POST /v1/scenes/{id}/merge-previews`（等价于 8.2 的 `dryRun`，也可独立提供）返回将产生的文档、预算编译结果与预期冲突。
- **验收标准**：预览不写状态；预览的预算结果与真正提交一致。

## 9. 团队操作规范（可直接贴进编辑器手册）

### 9.1 每次编辑

1. 打开场景先 `GET`，再冻结基线快照；记录 `revision`、`snapshot.id`、`snapshot.digest`。
2. 先写意图（图层 ID、世界坐标位移、素材摘要期望），再改文档。
3. 保存只用「当前修订」；不使用缓存的旧修订。
4. 收到 409：重新 `GET` → 判定表 → 重放意图 → 重新提交一次 → 仍 409 转人工。
5. 提交成功后冻结新快照，渲染并与基线比较；把比较结果附在提交记录里。

### 9.2 禁止事项

- 禁止把 409 当作「刷新修订号」的信号后重放旧文档。
- 禁止在整合时用数组下标定位图层，只用图层 ID 和相对锚点。
- 禁止在祖先链变化后直接复制后代的局部变换字段。
- 禁止为了通过保存而临时删除退役素材引用；先做素材决策。
- 禁止把归档/恢复当作撤销，或用旧检出、旧交换包覆盖规范场景。
- 禁止把 `scene.saved` 事件当作变更审计，它不含修订与摘要。

### 9.3 冲突提交的审查清单

- [ ] 基线修订、基线快照与摘要已记录
- [ ] 当前修订是提交时的最新修订（提交前刚读取）
- [ ] 图层 ID 全树唯一，未被静默改名/复用
- [ ] 层序按锚点表达，插入点经作者确认
- [ ] 祖先链变化已重算后代局部值，并给出世界坐标依据
- [ ] 素材引用全部 `available`；改指/删除已由素材负责人确认
- [ ] 场景名、画布尺寸、背景已显式决定
- [ ] 新快照摘要与基线摘要不同，像素差异只落在意图区域
- [ ] 取舍与决策人写入提交记录

### 9.4 事故处理

| 症状 | 判断 | 处理 |
|---|---|---|
| 保存 409 `scene revision changed` | 基线过期 | 按第 4 节重新整合；不要循环重试 |
| 保存 409 `scene is archived` | 场景被归档 | 找归档人确认；恢复后重新 `GET`，不要重放旧稿 |
| 保存或冻结 409 `…unavailable asset` | 引用已退役素材 | 按 5.3 做素材决策；不要绕过 |
| 保存 400 `unknown field` | 客户端发送了未实现字段（如 `edits`） | 退回整份 `document`；这正是「没有局部合并」的证据 |
| 提交 429 | 渲染预算或队列不足 | 缩小场景/减少图层后重新整合；429 不写入 |
| 已提交但画面缺层 | 可能发生过整份重放 | 用快照摘要与事件时间线定位，从基线快照恢复内容到新分叉，再人工整合 |
| 恢复归档后内容「不对」 | 把恢复误当撤销，或恢复了旧检出 | 以快照为准核对；用当前文档重新整合 |

## 11. 已知边界与开放问题

1. **单写实例**：服务用进程内互斥与整状态原子替换；跨进程/跨机器共享写入未验证。多编辑器并发最终仍序列化到一个实例，修订检查有效，但不能替代客户端整合。
2. **容量**：场景 ≤200 图层、≤8 层嵌套、画布每边 ≤1536、编译预算 4000 万图层像素。整合时新增图层可能触发 429，需在合并前评估。
3. **快照只增不减**：快照没有删除入口；用「每次编辑冻结基线」会产生长期记录，部署需按数据量规划状态盘。
4. **事件截断**：只保留最近 500 条，且不含修订/摘要，不能作为冲突审计的唯一来源。
5. **像素比较的边界**：只比较同尺寸输出，尺寸不同直接 409；`changedPixels`/`maxDelta` 只能说明「画面变了多少」，不能说明「是哪一层、哪个人改的」。因此重大结构改动仍须同时核对图层 ID 序列、世界包围盒与意图记录，不能只看像素计数。
6. **未决问题**：是否需要引入操作者身份（当前所有写入无 actor）；是否需要场景级锁或编辑租约；是否需要把「意图记录」作为服务端一等实体。这些都需要新能力，不能在本规范中假定。
